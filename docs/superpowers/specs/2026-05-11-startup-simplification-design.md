# 启动方式简化设计

## 背景

当前仓库的启动流程更偏向开发者使用：

- 后端通过 `bootstrap.ps1` 启动
- 前端通过 Vite 开发服务器单独启动，默认地址为 `127.0.0.1:41778`
- 后端 API 默认地址为 `127.0.0.1:41777`
- `scripts/opencode-usage.ps1` 可以协调前后端，但本质上仍是开发式包装

这套方式适合开发调试，但对于日常使用来说过于复杂。目标是让用户只运行一个脚本，就能直接打开仪表盘首页，而不需要手动分别启动前端和后端。

用户已经明确的需求如下：

- 使用“脚本一键启动”的形式
- 优先优化“日常使用”体验，而不是“开发调试”体验
- 可以接受首次手动执行一次构建，之后再简化为双击启动

## 目标

1. 提供一个面向日常使用的单一启动脚本。
2. 在正常使用场景中，不再要求用户分别启动前端和后端。
3. 在使用模式下，让后端成为唯一对外暴露的访问入口。
4. 保留当前基于 Vite + 后端服务的开发工作流。
5. 启动失败时，向非开发者输出可操作、可理解的错误提示。

## 非目标

- 本次不做 `.exe` 打包。
- 本次不做首次自动构建。
- 本次不移除现有 `npm run dev` 开发流程。
- 本次不尝试把开发模式和使用模式强行统一成同一种运行结构。

## 备选方案

### 方案 A：保持现状，只增加一个总启动脚本

保持现有 Vite 开发服务器和后端服务不变，只新增一个脚本，负责同时拉起前后端并打开浏览器。

**优点**
- 改动最小
- 交付最快

**缺点**
- 本质上仍然是开发运行时
- 日常使用仍依赖 Vite 开发服务器
- 仍然保留双端口和双进程的用户心智负担

### 方案 B：增加“使用模式”启动脚本，由后端直接托管前端构建产物

先对前端执行一次构建，然后由后端直接提供 `dist/client` 中的静态文件，同时继续提供 API 和鉴权接口。新增一个面向用户的启动脚本，负责启动后端并打开浏览器。

**优点**
- 最符合“只运行一个东西即可打开主页”的目标
- 日常使用不再依赖 Vite
- 结构简单、稳定
- 可以复用现有的后端生命周期脚本

**缺点**
- 需要后端支持静态文件托管
- 首次使用前需要手动构建一次
- 前端代码更新后，需要重新构建才能在使用模式下看到最新页面

### 方案 C：首次自动构建，并在后续自动判断是否需要重建

在方案 B 基础上，让启动脚本在首次运行时自动 build，后续根据源码与 `dist/client` 的状态决定是否提示或触发重建。

**优点**
- 对最终用户最省心

**缺点**
- 启动逻辑明显复杂化
- 启动耗时不可预期
- 自动重建判断规则容易引入边界问题和维护成本

## 推荐方案

采用 **方案 B**。

这个方案最贴合当前需求：既能实现“日常使用时一键打开主页”，又不需要过度设计复杂启动器，也不会破坏当前开发工作流。

## 设计方案

## 1. 运行模式划分

仓库将明确支持两种启动模式。

### 使用模式

- 唯一对外入口为 `http://127.0.0.1:41777`
- 后端同时提供：
  - `/api/*`
  - `/auth/*`
  - 前端静态资源（来自 `dist/client`）
  - 首页 `/`
- 用户通过单个 PowerShell 脚本启动应用：`start-app.ps1`

### 开发模式

- 保持当前行为不变
- 后端仍运行在 `127.0.0.1:41777`
- Vite 开发服务器仍运行在 `127.0.0.1:41778`
- `npm run dev` 继续作为前端开发入口

这样可以把“日常使用的简洁性”和“开发调试的便利性”分开处理，互不干扰。

## 2. 后端托管前端静态资源

需要扩展 `server/main.ts`，使后端在存在构建产物时，可以直接对外提供前端页面。

### 行为要求

- 当 `dist/client` 存在时，后端应能够：
  - 返回首页 `/` 对应的 `dist/client/index.html`
  - 提供 `dist/client/assets/*` 等静态资源
- API、鉴权、健康检查等现有后端能力保持不变
- 使用模式下，浏览器访问后端地址即可打开完整页面

### 设计约束

- 静态文件托管不能干扰以下路径：
  - `/api/*`
  - `/auth/*`
  - `/health`
  - diagnostics 相关路径
- 开发模式下仍需兼容当前 Vite 代理机制
- 使用模式运行时不能依赖 Vite

## 3. 新增面向用户的启动脚本

在仓库根目录新增脚本：

- `start-app.ps1`

### 职责范围

1. 检查 `dist/client/index.html` 是否存在。
2. 如果构建产物不存在，立即停止，并清晰提示用户先执行：
   - `npm ci`
   - `npm run build`
3. 通过现有 `bootstrap.ps1 start` 启动后端。
4. 等待 `http://127.0.0.1:41777/health` 健康检查成功。
5. 自动打开浏览器到 `http://127.0.0.1:41777`。
6. 如果后端已经在运行且健康，则不重复启动，只直接打开浏览器。

### 明确不负责的事情

- 不自动执行 build
- 不启动 Vite 开发服务器
- 不替代 `bootstrap.ps1`

这样可以保证：用户脚本保持简单，而后端生命周期管理仍集中在现有脚本中。

## 4. 启动交互与错误处理

这个脚本应表现得像“应用启动器”，而不是“开发脚本包装器”。

### 构建产物缺失

如果 `dist/client/index.html` 不存在，应直接提示：

```text
未发现前端构建产物。
请先执行：
  npm ci
  npm run build
然后重新运行 start-app.ps1
```

此时脚本应立即退出，不做部分启动。

### 启动成功

启动成功后，应输出简洁、面向用户的状态，例如：

```text
[OK] Backend ready
[OK] Frontend served from dist/client
[OK] Opening browser: http://127.0.0.1:41777
```

### 后端启动失败

如果后端启动失败，应保留 `bootstrap.ps1` 现有日志和诊断能力，但同时补充用户能理解的排查提示，例如建议检查：

- `.env` 或 `dashboard.config.json`
- `OPENCODE_DB_PATH`
- `41777` 端口是否被占用
- `.run/` 下的日志文件

### 浏览器自动打开失败

如果后端已经健康，但浏览器无法自动打开，不应视为整个启动失败，而应提示：

```text
服务已启动，但未能自动打开浏览器。
请手动访问：
http://127.0.0.1:41777
```

### 已在运行

如果后端已经在运行且健康，则不再启动第二个实例，而是复用现有服务，直接打开主页。

## 5. 文档调整

README 应明确区分两种使用路径。

### 日常使用路径

```powershell
npm ci
npm run build
pwsh -File .\start-app.ps1
```

这部分应成为文档中最显眼的启动方式。

### 开发调试路径

```powershell
pwsh -File .\bootstrap.ps1 start
npm run dev
```

这部分保留给仓库维护者或开发者使用。

## 6. 涉及的文件改动

### `server/main.ts`

- 增加构建后前端静态资源托管能力
- 确保 API / auth / health 等路由优先于静态回退
- 在使用模式下通过后端对外暴露首页

### `start-app.ps1`

- 新增根目录用户入口脚本
- 检查前端构建产物是否存在
- 调用 `bootstrap.ps1` 启动后端
- 等待健康检查通过
- 打开浏览器
- 妥善处理“已在运行”和“浏览器打开失败”这两类情况

### `README.md`

- 将“日常使用方式”调整为主入口
- 保留“开发方式”作为次级说明

此外，项目中凡是默认把 `41778` 视作主页入口的说明文字，也应同步改为更符合“使用模式”的表述。

## 7. 测试与验证策略

验证应同时覆盖“使用模式”和“开发模式未受破坏”两方面。

### 使用模式验证

- 后端访问 `/` 时能返回 `dist/client/index.html`
- 前端构建产物可通过后端地址正常加载
- API 在同一后端地址下仍能正常工作
- `start-app.ps1` 在缺少构建产物时会拒绝运行并输出清晰提示
- `start-app.ps1` 在后端健康时能打开正确地址
- 重复运行 `start-app.ps1` 不会创建重复的后端实例

### 开发模式验证

- `npm run dev` 仍能在 `41778` 提供前端页面
- Vite 到后端的代理仍正常工作
- 现有后端 API 路径行为不发生破坏性变化

### 故障路径验证

- 缺少构建产物时的提示足够清晰
- 后端启动失败时会给出可执行排查建议
- 浏览器自动打开失败时，服务仍然可用

## 8. 成功标准

当以下条件同时满足时，说明本次改动成功：

1. 用户只运行一个脚本就能进入仪表盘首页。
2. 使用模式下首页由 `127.0.0.1:41777` 提供。
3. 日常使用时不再需要手动运行 Vite。
4. 现有开发工作流仍然可用。
5. 启动失败时，用户无需阅读源码也能理解下一步该如何排查。
